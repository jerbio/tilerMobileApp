## 1. Background & goal

TileShare lets one user hand work to other people: a sender creates a **cluster**
of one or more **tilettes** (tasks) and invites **recipients** by email/phone;
each recipient accepts or declines, and an accepted tilette becomes real tiles on
their schedule. The feature works end to end but the UI grew screen by screen:
status is invisible in lists, the recipient's core decision is buried, three
near-identical detail screens carry ~900 duplicated lines, and half the model
(Notes, Address, Schedule pattern) is unreachable.

**Goal:** (a) a person sees at a glance **what needs their attention** and can
act from the list, (b) an owner sees how each cluster is going, (c) the three
ways of sharing — **Broadcast, Project, Class** — are first-class and visibly
different, (d) the details the model already supports ship, (e) the screens
share one structure instead of three copies.

### 2.3 Findings that drive the redesign

1. **Lists show no status** ([tileShareSimpleWidget.dart](../lib/routes/authenticatedUser/tileShare/tileShareSimpleWidget.dart)): 12 px name, deadline, comma-joined contacts. No RSVP summary, progress, or "needs your response". `DesignatedUserCircle` exists but only renders in tilette rows.
2. **The recipient's decision is buried**; Accept/Decline are stacked buttons on a dense card; Accept silently runs `analyzeSchedule` + `buzzSchedule`; no undo, no confirm; forecast is a binoculars icon.
3. **Three near-duplicate detail screens** ([single](../lib/routes/authenticatedUser/tileShare/singleTiletteTileShareDetail.dart), [multi](../lib/routes/authenticatedUser/tileShare/multiTiletteTileShareDetail.dart), [inbox](../lib/routes/authenticatedUser/tileShare/inboxMultiTiletteTileShareDetail.dart)) with copied load/error/header code, `screenHeight − 400` layout arithmetic, and a bento *mode toggle* that pushes a second create screen.
4. **Model fields with no UI:** `Notes`, `AddressData`, `SchedulePattern` (cluster); `AddressData`, `NoteMiscData` (tilette — mapped by `NewTile.toClusterTemplateTileModel` but the add-tilette sheet has no inputs); `priority`.
5. **Schedule-card indicator is a placeholder:** two identical person icons ([enhancedTileCard.dart:1619](../lib/components/tileUI/enhancedTileCard.dart)).
6. **Fire-and-forget writes** (contact add/remove — [contact-input-field-improvements.md](contact-input-field-improvements.md) 3.3/3.5); swipe-to-dismiss deletes with no confirmation; every list row is re-keyed with a fresh `Utility.getUuid` on each build (defeats animation and resets swipe state); hard-coded English strings; dead code; stray `print`s.
7. **Chrome is out of step with Daily**; Activity is a peer tab of Sent/Received although it is a log of them.
8. **Test coverage:** only `tile_share_activity_test.dart` (+ comments API). Its canonical fixture is read from the backend repo by relative path (`../../WagTapWeb/…`).
9. **The activity client discards server data:** completions, invitations-to-me, what changed in an edit (incl. the old/new deadline), who was added (`targetUserId`) and per-event dismissal are all available from the server but unread. The feed clears itself on every reload (flash/jump).

## 5. Target experience

### 5.1 Modes at a glance

|  | One task | Many tasks |
|---|---|---|
| **Everyone has their own instance** | **Broadcast** | **Class** |
| **Everyone shares one instance** | _(claim-style — later)_ | **Project** |

| | Broadcast | Class | Project |
|---|---|---|---|
| Recipient gets | their own copy of the task | their own copy of the whole project | a role in one shared project |
| Owner sees | roster: RSVP status + each person's progress on the one task | roster: RSVP status + per-person, per-task progress segments | task board: who owns which task + each task's own progress |
| Progress shown | per recipient, on the one task | per person, per task (segments) — never one total | per task on the board — never one total |
| Accept means | I'll do this task | I'll do this project | I'll take part (and my tasks) |
| Backend `mode` | `broadcast` (legacy: `isMultiTilette == false`) | `class` | `project` (legacy: `isMultiTilette == true`) |

- *Changed / At risk:* one CTA ("Review changes", "Review plan").
- *Responses (owner):* "View" / "Resend" (delivery failed) / "Reassign" (later).

**Cluster card** — mode badge (icon + label) · name · role line ("from @sarah" / "You") · due chip (urgent < 48 h) · and by mode and role:

### 5.9 Accept preview (T21-T26)

The same outcome as the web's schedule preview - *see when it lands before you accept, change nothing by looking, choose between genuinely different arrangements, accept flexibly or lock one session, and always be told the truth* - in a phone-shaped flow, not a port of the desktop modal.

```
┌ ‹  Content & Marketing   ⟳ ┐
│  day strip: Fri 24  ‹ ›     │  ONE day, read-only context
│   9 ┌┄┄┄┄┄┄┐ ← proposed     │  (teal dotted block, your tiles in their colours)
├──── draggable sheet ────────┤
│ ● Suggested · Fri 9–10 AM   │  the answer: date, time, duration, time zone
│   1 hr · moves 2 flexible   │
│ [ Accept ]  [ Accept & lock]│  in the collapsed sheet, at the thumb
│  Tiler may move flexible…   │
│ ▸ Other arrangements        │
│ ▸ Sessions · Details        │
│   Decline                   │
└─────────────────────────────┘
```

* **The strip is context, the sheet is the product.** The selected-time strip and both accept actions are visible with the sheet collapsed; expanding it shows the sessions, the deadline and description (kept separate from the scheduled time) and the scheduling issues.
* **Sessions are a list.** Split work shows every session (date, start-end, duration); the highlighted one is the lock target and moves the strip; one visible interval never stands for the whole task. A session outside the returned window keeps its explicit date and “Scheduled outside the displayed window”.
* **Other arrangements** open in the same sheet as cards (time, duration, what they move, a clear selected state - no padlocks). Tapping one **swaps the whole arrangement at once** (every option embeds its full preview; no request), keeps the list open, and keeps both accept actions beside the new time. “Find another time” asks for more; “No different time found” is a valid result; “Back to preview” keeps the choice.
* **Outcome states, each honest:** *Loading* (a real skeleton - forecasts are slow - and the screen can be left); *Unsupported* (`alreadyAccepted`, `missingFutureDeadline`, `unsupportedConstraints`: said plainly, plain Accept / Decline remain on the card); *Cannot fit / Not scheduled / Scheduling conflict* (error or warning hue **plus** an icon and words; Accept disabled; other arrangements become primary); *Scheduling issues* (a collapsible group - unscheduled work and conflicts - with duration and allowed window, never drawn as appointments); *Stale* (409 `previewExpired` / `scheduleChanged`: the selection summary is kept, “Refresh preview”); *Preview error* (retry, last valid preview kept, never a new time over an old strip); *Unavailable* (404 / 503, neutral, return).
* **After Accept:** “Adding to your calendar…” with duplicates disabled (the request runs the whole acceptance, so it can take a while, and its answer is the outcome - there is no polling); `completed` shows “Added to your calendar” with “View in calendar”; **`needsreview` is its own message** (added, scheduling not confirmed) with the same link; `rejected` allows a fresh review; an uncertain result (timeout, lost connection, app closed) shows “We couldn't confirm” and **repeats the same request** - which returns the stored outcome or resumes the interrupted acceptance - or reads the status once; never a second independent accept.
* **Hues carry meaning in light and dark** (teal = suggested / selected, success = accept, warning = unscheduled, error = cannot fit / decline), always paired with text or an icon; the sheet snaps and the strip fades respect reduced motion.
* **Entry:** “Check fit” / “Preview schedule” on a Broadcast invitation (card, row, detail) and later on a Project task row. Inline Accept never passes through it (T22); Class and Project skip it (T23).

## 7. No-snap & interaction rules (T11)

- Item moves (accept/decline/undo, resolve), deletes, filter switches and reloads animate; row keys are the cluster / designated-tile id (never a fresh UUID); pagination appends, pull-to-refresh merges by id; scroll offset and swipe state survive a reload.
- **The gate (9.16j):** `test/tileshare_no_snap_test.dart` hosts the hub (Clusters, Attention) and the detail (Tilettes, Board, Participants, the banners) against the real cubits, applies one outside change, and checks (1) at t = 0 no visible keyed row has moved 4 px or more, and (2) over the next frames no row makes more than half of its move in one frame (so a move put off by a frame and then made at once still fails). Two shared pieces carry it: **`AnimatedKeyedColumn`** (`widgets/animatedKeyedColumn.dart`) for lists - arrivals grow in, departures shrink out where they were - and **`RevealSlot`** (`widgets/revealSlot.dart`) for anything that comes and goes (banners, alerts, warnings, the answer buttons) - it grows in, and on the way out keeps showing while it shrinks and fades. Covered (9.16j-k): the hub, the detail's Tilettes / Board / Participants / Overview, the banners, the recipient's commitment, and the tilette sheet's people list and callouts. The sheet's checks live with its rig in `tileshare_task_sheet_test.dart` (group *no snap*); both harnesses share `test/helpers/tileshare_no_snap.dart`.
- Optimistic actions (T8) roll back with an animation and a localized message — never a silent revert.
- Every failure shows a localized message with Retry; no raw exception text. Hard-coded strings are moved into `.arb` as touched.
